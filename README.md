# GenAR Challenge — Version 0

Takes raw adverse event data for Bisoprolol and generates a PADER report.
Rule: every number in the report comes from Python, never from the AI.

# Video Walkthrough 
https://drive.google.com/file/d/1A6h6jTus5AYFJU0aWoG2ETue8OLbDSdt/view?usp=sharing

## Run it

```bash
pip install pandas openpyxl

python report_generator.py              # generates 6 sections, queues for review
python human_review.py list              # see what's pending

python human_review.py approve narrative_summary
python human_review.py approve summary_analysis
python human_review.py approve reaction_analysis
python human_review.py approve alerts
python human_review.py approve trends
python human_review.py approve history_of_actions

python report_generator.py --render-only # writes report_output.md
```

To use the real Claude API instead of pre-written text:
```bash
set ANTHROPIC_API_KEY=sk-ant-...
python report_generator.py --online
```

## Architecture

```
bisoprolol.xlsx
   -> data_loader.py     dedupe cases, split multi-reaction rows
   -> analysis.py        every count: cases, demographics, top reactions, outcomes, alerts, trend
   -> context_builder.py builds a small JSON packet per report section
   -> prompts.py          system rules + one template per section
   -> llm_client.py       only file that calls Claude
   -> human_review.py     approve/flag before anything is final
   -> report_generator.py assembles report_output.md
```

## AI vs Python — why split it this way

Python does all the counting. Total cases, breakdowns, top reactions — these are exact
answers from `.value_counts()` / `.groupby()`. No reason to let a model guess something
Python already knows for certain.

AI only writes the paragraphs. Turning a JSON packet of numbers into readable sentences
is a writing task, not a math task — that's the one thing worth using a model for here.

Tables in the final report (case list, reaction counts, monthly counts) are also pulled
straight from `analysis.py` — never written by the model, so there's zero risk of it
messing up a number in a table.

## The prompts

System prompt (same for every section):

```
You are drafting one section of a PADER (Periodic Adverse Drug Experience Report).

Rules:
1. Only use numbers given to you in the data below. Never guess a number that isn't there.
2. Never turn an observation into a safety conclusion.
3. If something is missing, say so. Don't invent it.
4. Neutral, factual tone.
5. Write only the section text, nothing else.
```

Then one short template per section. Example (Narrative Summary):

```
Section: Narrative Summary and Analysis

data:
{data}

Write 2-3 paragraphs covering case volume, seriousness split, top reactions,
outcomes, and demographics — using only the numbers above.
```

`{data}` is filled from `context_builder.py` with only the numbers that section needs.
Alerts section gets a note that its criteria don't sum to the total (they overlap) —
narrative summary doesn't get that note because it never shows that table.

## How it stays grounded

- Model never sees the raw spreadsheet, only the small JSON packet for its own section
- System prompt says: only use numbers you were given
- Tables in the report are built straight from `analysis.py`, model never touches them
- `case_index()` lists all 1,024 cases individually — any number in the report can be
  traced back to specific cases
- Nothing reaches the final report without going through `human_review.py` approval

## Evaluating at scale (1,000 reports)

1. Re-run the analysis function behind every number in the generated text, check it matches. Catches hallucinated numbers automatically.
2. Rule checks per section — e.g. alerts section should never say its numbers sum to the total.
3. For anything a rule can't catch (tone, overstating a trend), sample a few reports for a human to actually read instead of reading all 1,000.

## What's missing / known limitations

- No API key was available while building this, so `report_output.md` was generated by running the exact prompts through Claude by hand instead of the script calling the API. `llm_client.py` is real working code for the actual call.
- No System Organ Class field in the data, only reaction names (MedDRA Preferred Term). Didn't try to guess SOC groupings.
- No product label was given, so can't say if a reaction is "expected" or not. Skipped, not guessed.
- Age buckets (0-17/18-40/41-64/65+) are ones I picked myself — the data's own age-group field is mostly blank.
- Reaction and outcome lists in each row are matched by position (1st reaction = 1st outcome). True for this dataset, but not something the file format guarantees.
- No retry logic if the API call fails.
- No log of who approved what, or when.

## Would this work for other report types (PSUR, PBRER, DSUR)?

`data_loader.py` and `analysis.py` don't care what report type is asking — they'd work
as-is. `context_builder.py` and `prompts.py` are currently PADER-only (hardcoded section
list). See `version1/DESIGN.md` for how I'd fix that.
